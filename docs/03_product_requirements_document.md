## 2. Executive Summary

The platform is a closed institutional restaurant ecosystem connecting verified Bennett University members with partner restaurants. Users can discover nearby restaurants, view menus, active restaurant offers, ratings and reviews, and pre-book based on date, time and guest capacity.

The unified Management Portal contains three operational roles: Super Admin, Admin and Restaurant. Super Admin governs the platform; Admin represents the restaurant owner/manager and controls the restaurant, offers, staff and analytics; Restaurant represents restaurant staff and handles day-to-day booking operations.

---

## 3. Problem Statement

Students and faculty need a trusted, institution-focused place to discover nearby partner restaurants, compare restaurant information, see current offers, read customer feedback and reserve in advance. Partner restaurants need a focused channel to serve the institutional community and manage demand generated by reservations.

The platform addresses both sides through institutional verification, restaurant discovery, pre-booking, and role-based access control.

---

## 4. Product Vision

Build the preferred restaurant discovery and pre-booking layer for institutional communities, starting with Bennett University, where verified members can easily discover nearby restaurants and restaurants can efficiently manage reservations and customer demand with an elegant, resilient user experience.

- Create an institution-exclusive restaurant discovery and pre-booking experience.

## 7. Authentication & Institutional Verification

The initial institution is Bennett University. The backend must enforce the approved institutional email domain. The account verification flow is designed as:

**Registration → Pending Approval → One-Time Verification Code → Verified Account**

| Stage | System Behavior |
|---|---|
| **Registration** | User submits name, institutional email and password. |
| **Domain Validation** | Backend verifies that the email belongs to an approved institution domain. |
| **Pending** | Account enters PENDING verification status. |
| **Approval** | Super Admin reviews and approves or rejects the user. |
| **Verification Code** | Approved user receives a one-time verification code. |
| **Verification** | Valid, unexpired code changes the account to VERIFIED. |
| **Access** | Only authorized verified users can use protected user features. |

### Rules
- Initial Bennett domain: `@bennett.edu.in`
- Verification codes must be single-use, time-limited and securely stored/hashed
- Verification attempts must be rate-limited
- Use an `Institution` entity so Bennett is not hardcoded throughout the application

## 12. Pre-Booking

Pre-booking is the core transactional feature. Users select a restaurant, date, time and guest count, with an optional special request. Individual table selection is deliberately not exposed to users.

| Field | Requirement |
|---|---|
| **Restaurant** | Must be approved and active. |
| **Date** | Must satisfy booking window and restaurant availability. |
| **Time** | Must fall within operating hours and configured availability. |
| **Guests** | Positive integer within restaurant-defined limits. |
| **Special Request** | Optional user text. |
| **Booking ID** | Unique system-generated identifier. |
| **Status** | PENDING, CONFIRMED, REJECTED, CANCELLED, COMPLETED, NO_SHOW. |

### Rules
- Recommended lifecycle: `PENDING → CONFIRMED → COMPLETED`
- No table selection
- No payment is collected through the platform
- No waitlist is created when capacity is unavailable
- Backend availability/capacity validation must be transactional
- Table assignment, if required, remains a restaurant-side operational responsibility

## 18. Role-Based Access Control (RBAC) Model

Authorization uses **Role-Based Access Control (RBAC)** coupled with institutional and restaurant resource scoping. Roles determine user capabilities, and tenancy scoping ensures actors only mutate resources assigned to them.

| Role | Scope | Permitted Capabilities |
|---|---|---|
| `SUPER_ADMIN` | Global Platform | Global governance, institution lifecycle, user approvals, restaurant verification, platform metrics, review moderation |
| `RESTAURANT_ADMIN` | Assigned Restaurant (`restaurantId`) | Restaurant profile editing, menu engineering, offer creation/lifecycle, availability slot definitions, staff roster, restaurant analytics |
| `RESTAURANT_STAFF` | Assigned Restaurant (`restaurantId`) | Operational daily booking workflow: confirm, reject, mark complete, mark no-show; view special requests and daily arrival roster |
| `USER` | Own Account (`userId`) | Institutional registration, discovery search/filter, view restaurant profiles, pre-book reservation, manage own bookings, write reviews |

### Key Rules
- Every protected API request must authenticate the caller via verified JWT and enforce role authorization via middleware.
- Restaurant Admin and Restaurant Staff roles validate that `req.user.restaurantId` matches the targeted restaurant resource.
- User operations validate that `req.user.id` strictly matches the booking or review owner.
- Super Admin possesses override privileges for platform oversight and moderation.
- Resource ownership is always verified from authenticated token state, never trusted from client-supplied URL or body IDs.

## 21. Database & Prisma ORM Rules

- Manage all schema modifications using version-controlled Prisma migrations (`npx prisma migrate dev`).
- Enforce relational integrity with foreign keys (`@relation` references with `onDelete: Cascade` / `Restrict`).
- Apply compound unique indexes where business logic dictates (e.g. `@@unique([restaurantId, slotDate, startTime])`).
- Wrap capacity checks and booking creations in atomic Prisma transactions (`prisma.$transaction`) with row-level locks.
- Prevent race conditions and overselling via database constraints.
- Store timestamps in UTC ISO-8601, formatted to institutional local timezone on the client.
- Preserve historical and audit records using soft delete / status fields.

## 22. High-Level Architecture

```
React User Portal + React Unified Management Portal
        ↓
Express.js REST API Middleware (CORS, Rate Limit, Auth, RBAC)
        ↓
Domain Services (Auth, Restaurant, Menu, Offer, Booking, Review, Analytics)
        ↓
Prisma ORM Client (@prisma/client)
        ↓
PostgreSQL Database (Transactional System of Record)
```

| Layer | Responsibilities |
|---|---|
| **Frontend** | React SPA, routing, Lucide icons, soft elegant design system, pre-built complete flow states. |
| **API** | Express REST endpoints, Zod schema validation, JWT auth and RBAC scoping middleware. |
| **Authentication** | Argon2id/bcrypt credential hashing, 6-digit OTP verification, secure HTTP-only cookies. |
| **RBAC Layer** | Role verification (`SUPER_ADMIN`, `RESTAURANT_ADMIN`, `RESTAURANT_STAFF`, `USER`) + restaurant tenancy check. |
| **Domain Services** | Restaurant, menu, offer, booking lifecycle, review eligibility, and notification logic. |
| **ORM / Data Access** | Prisma ORM with connection pooling, parameterized queries, and typed client. |
| **Database** | PostgreSQL transactional system of record with row-level locking. |
| **Storage** | Object storage/CDN for restaurant/menu images. |
| **Async Processing** | Serverless/background processing for notifications and non-critical analytics. |

## 23. Serverless Requirements

- Backend services must be stateless.
- Do not depend on persistent in-memory state between requests.
- Do not depend on local filesystem persistence.
- Use managed PostgreSQL with serverless-suitable connection pooling.
- Use external/object storage for uploaded images.
- Use secure session/token management.
- Use asynchronous execution for notifications and non-critical background work.
- Keep booking consistency transactional in PostgreSQL.

## 25. API Authorization Rules

- Authenticate all protected operations using verified JWTs.
- Evaluate the RBAC role and restaurant tenancy scope before reading or mutating resource data.
- Never trust `restaurantId`, `userId` or `role` supplied by the client URL or payload.
- Derive subject identity and permissions directly from the authenticated session/token.
- For `RESTAURANT_ADMIN` and `RESTAURANT_STAFF`, verify active membership against the targeted restaurant.
- Return safe authorization errors (e.g. 403 Forbidden with clear code) without leaking data existence.
- Record privileged actions in immutable audit logs.

## 27. Security Requirements

- Hash passwords using Argon2id or bcrypt.
- Use secure session/token management via HTTP-only, SameSite cookies or Authorization headers.
- Validate institutional email domains on the backend.
- Enforce RBAC on every protected resource operation.
- Enforce resource ownership and tenancy server-side.
- Hash verification codes and enforce 10-minute expiration, single use and attempt limits.
- Validate and sanitize request payloads using Zod schemas.
- Apply rate limiting to authentication and verification endpoints.
- Use Prisma ORM parameterized queries to prevent SQL injection.
- Validate uploaded media MIME type and enforce 5MB file limits.
- Never expose passwords, verification codes or sensitive authorization data.
- Maintain audit logs for privileged actions.
- Use HTTPS and secure environment/secret management in production.

## 28. UI/UX Design System, Elegance & Flow Coverage

### 28.1 Aesthetics & Soft Color Palette
The interface adopts an elegant, calm luxury institutional visual language:
- **Soft Neutrals:** Warm Alabaster (`#FBFBFA`), Soft Slate (`#F8FAFC`), Muted Stone (`#71717A`), Deep Charcoal (`#18181B`).
- **Subtle Primary:** Refined Midnight Slate / Classic Indigo (`hsl(222, 47%, 45%)`) providing prestige without aggressive saturation.
- **Muted Semantics:** Soft Sage for success (`hsl(152, 45%, 42%)`), Dusty Rose for errors (`hsl(0, 52%, 58%)`), Warm Sand for warnings (`hsl(36, 65%, 55%)`).
- **Tactile Micro-Animations:** Fluid hover states, subtle elevations (`shadow-sm` transitioning to `shadow-md`), soft button depressions (`active:scale-[0.98]`), and gentle card scaling (`hover:scale-[1.01]`).

### 28.2 Strict Iconography Standard (Zero Emojis in Code)
- **Strict Rule:** Emojis are prohibited in all code, templates, toasts, badges, and markup.
- **Lucide Icons:** All icons must be imported from `lucide-react` (e.g., `<CheckCircle2 />`, `<AlertCircle />`, `<XCircle />`, `<SearchX />`, `<WifiOff />`, `<ShieldAlert />`, `<Calendar />`, `<Clock />`, `<MapPin />`).

### 28.3 Mandatory Pre-Designed Flow States
To prevent broken user flows, seven comprehensive state views are standardized across both portals:
1. **Empty State:** Illustrated minimalist card, friendly explanation, primary action CTA (e.g. "Discover Restaurants").
2. **Loading State:** Soft shimmering skeletons matching exact target layout dimensions to avoid Cumulative Layout Shift (CLS).
3. **Error State:** Dedicated card with human-readable error title, diagnostic message, and "Try Again" / "Go Home" actions.
4. **No Internet State:** Offline indicator bar/screen triggered by network listener with auto-reconnect retry button.
5. **No Search Results State:** Helpful feedback screen with Lucide `SearchX`, suggested keywords, and a "Clear all filters" CTA.
6. **Permission Denied (403) State:** Institutional boundary screen explaining required role with a "Return to Dashboard" CTA.
7. **Success State:** Refined check confirmation screen with summary card, booking reference code, and next steps.
